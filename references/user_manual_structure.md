# 用户手册编写规范

用户手册应参照真实软件随附的用户说明编写，固定为五个顶层章节。正文由模型依据项目证据撰写，脚本只负责排序、编号、排版和校验。

## 固定章节

正式章节标题使用阿拉伯数字序号，顺序不可改变。第一页采用宋体一号居中封面，第二页为带点线和页码的目录，正文从第三页开始：

1. **系统功能概述**：先概括软件定位、目标用户、业务范围和整体功能，再按总分关系介绍主要功能。
2. **软件安装与配置**：写明真实安装方式、运行依赖、配置项、启动方式和配置完成后的可见结果；没有安装步骤的软件也要说明其实际部署或直接访问方式。
3. **软件使用说明**：按真实页面、导航入口或核心流程逐节介绍功能，配用已核实的截图；没有真实截图且用户选择时，可用简单界面示意图。每个模块须写清用途、入口、可见元素、用户动作、规则、反馈和边界。
4. **典型使用流程总结**：以一个或多个真实业务流程串起入口、关键操作、结果和产物，不重复逐模块说明。
5. **使用注意事项与常见问题**：记录真实运行限制、数据边界、权限或依赖问题，以及可执行的排查步骤。

`manual_modules` 只用于第 3 章；`operation_flow` 用于第 4 章；`manual_usage_notes` 与 `faq` 用于第 5 章。缺少真实证据时必须停止并补全业务理解，不得按模板猜测。

## 业务理解字段

业务理解 JSON 至少包含：

- `manual_function_overview`：第 1 章正文段落数组，先总览，再分项介绍。
- `manual_installation_config`：第 2 章正文段落数组，可附 `requirements` 表格。
- `manual_modules`：第 3 章功能模块数组。每项包含 `title`、`body`、`purpose`、`usage`、`entry`、`visible_elements`、`operation_steps`、`validation_rules`、`feedback`、`boundary`、`screenshot` 和 `evidence`。
- `operation_flow`：第 4 章流程段落数组，必须来自真实操作顺序。
- `manual_usage_notes`：第 5 章注意事项段落数组或条目数组。
- `faq`：第 5 章常见问题数组，每项含 `question` 与 `answer`。

`body`、`manual_function_overview`、`manual_installation_config`、`operation_flow` 和 `manual_usage_notes` 是模型直接撰写的正文；脚本不得拼装句子、改写术语或修补病句。

## 模块正文与截图

- 每个功能模块正文通常为 2 个短段落，目标 120 至 220 个中文字符，复杂模块上限 400 字。
- 正文应覆盖真实入口、用户可见元素、主要动作和结果反馈；规则与边界按项目实际情况补充。
- 不输出“进入方式：”“操作步骤：”等字段式小标题，不使用项目符号代替成文段落。
- 每幅截图使用 `图 <章号>-<章内序号>` 编号，并有独立图注。真实图片可来自用户截图、项目现有截图或用户提供的文档/PPT；须核对与模块一致，并保留来源。
- 若没有可用真实截图，可询问用户是否生成静态界面示意图；图注必须写明“界面示意，非实际运行截图”。用户选择跳过时保留 Word 中可见的截图预留文字。

## 截图来源

先检查项目、用户截图和用户文档/PPT 中是否已有可用图片。从文档/PPT 提取图片时保留文档名和页码/幻灯片号。仅在这些来源均无可用截图时，询问用户选择生成示意图或保留空位。示意图依据真实功能的源码证据，用简单 HTML/CSS 表达必要控件和流程，浏览器截图后保存 HTML、PNG、证据路径和清单；不得伪造软件真实运行结果。

## 写作约束

- 所有业务事实、按钮文案、操作顺序、状态、数值和错误提示都要能回溯到源码、项目文档或用户截图。
- 功能说明面向普通用户，解释架构、数据存放和运行依赖时才使用技术术语。
- 删除“旨在、赋能、一站式、显著提升”等空泛表达和重复模板句式。
- 设计取舍和边界情形只有在项目有证据时才写；写不出真实原因就不补空话。
- 常见问题必须是软件真实可能出现的问题，并给出按顺序执行的排查步骤。

## 自检

生成用户手册时同步写出 `草稿/用户手册自检记录.md/json`，至少检查：五章是否齐全、总分关系是否清楚、安装配置是否真实、功能模块是否覆盖入口/动作/反馈、截图编号和文件是否匹配、典型流程是否连贯、注意事项和 FAQ 是否可执行、是否存在套话或样例项目残留。
